# SDL3 + SDL_GPU shader-based renderer

## Why

Two pain points the current pipeline can't solve:

1. **Color cycling is broken.** The pure-RGBA Display refactor baked palette indices into RGB at draw time, so `Display::changePalette` only updates the table for *future* draws. Water shimmer, gold sparkle, lava flicker, sprite glow — all the indexed sprites that rely on rotating ranges 214-217, 218-221, 231-235, 238-241 are now static.

2. **Custom monsters want richer transforms than palette swaps.** Today every custom monster (Thor, Succubus, Azure Dragon, Blood Dragon, Avenger) is generated by remapping a base ICN through a `PaletteType` table. That works for "redder version of X" but is fundamentally limited to per-pixel index→index lookups. A shader stage opens the door to per-channel multiply/add, gradients, masks, alpha-driven outlines, and conditional remaps — all the transforms that today require shipping pre-rendered hi-res PNGs.

The previous markdown plans (`PURE_RGBA_DISPLAY_PLAN.md`, `PHYSICAL_RES_DISPLAY_PLAN.md`) flagged "color cycling postponed until a shader-LUT path lands" — this doc is that path.

A pragmatic interim alternative (game-resolution indexed shadow buffer + CPU-side palette walk on cycling tick) is described inline at the end of `PHYSICAL_RES_DISPLAY_PLAN.md`'s discussion. It ships cycling in ~200 lines but doesn't help the custom-monster transform story. This plan is for the full GPU path.

## Architecture

Three GPU textures + a fullscreen composite pass:

```
+--------------------------------------------------+
|  CPU: Display owns two physical-res buffers      |
|    _indexedBuffer  : R8   (palette index)        |
|    _data (RGBA)    : RGBA (already exists)       |
+--------------------------------------------------+
                      │  per frame:
                      │    SDL_UploadToGPUTexture x 2 (dirty rect)
                      ▼
+--------------------------------------------------+
|  GPU: SDL_GPU pipeline                           |
|    indexedTex   : R8                             |
|    rgbaTex      : RGBA8                          |
|    paletteTex   : RGBA8 256x1  (re-uploaded on   |
|                   each cycling tick, ~1KB)       |
|    compositePipeline + nearestSampler            |
+--------------------------------------------------+
                      │  draw fullscreen triangle
                      ▼
+--------------------------------------------------+
|  Fragment shader composites:                     |
|    idx = texture(indexedTex, uv).r * 255         |
|    if idx > 0.5: out = palette[idx]              |
|    else:         out = texture(rgbaTex, uv)      |
+--------------------------------------------------+
                      │
                      ▼
                   Swapchain
```

### Sentinel for "use RGBA"

`indexedBuffer[i] == 0` means "no palette index here, use the RGBA channel". Game palette index 0 is reserved/black in the original game's PAL, so picking 0 as the sentinel is safe — nothing visible should ever produce index 0 as a normal sprite pixel. (Worst case if it does: that one pixel falls through to the RGBA texture, which at draw time was filled with the same palette[0] color anyway. Visually identical.)

### Why dual-write instead of indexed-only

Some content is genuinely RGBA at the source — hi-res monster PNGs, video frames, spell-effect scratch buffers, anti-aliased shadows from `BlitRGBAScaled`. Quantising those to a palette index for storage would throw away the resolution gains the physical-res refactor was meant to deliver. The two channels coexist; whichever was written most recently per pixel wins via the sentinel.

### Shader (fragment, GLSL — translated to MSL/HLSL/SPIR-V via shadercross)

```glsl
#version 450

layout(set = 2, binding = 0) uniform sampler2D indexedTex;
layout(set = 2, binding = 1) uniform sampler2D rgbaTex;
layout(set = 2, binding = 2) uniform sampler2D paletteTex;

layout(location = 0) in vec2 uv;
layout(location = 0) out vec4 outColor;

void main() {
    float idx = texture(indexedTex, uv).r * 255.0;
    if (idx > 0.5) {
        // Palette LUT lookup. Texel center math: (idx + 0.5) / 256.
        outColor = texture(paletteTex, vec2((idx + 0.5) / 256.0, 0.5));
    } else {
        outColor = texture(rgbaTex, uv);
    }
}
```

A trivial fullscreen vertex shader emits a single triangle covering the viewport.

#### Phase 1A — surprises that needed real fixes (not just renames)

These came up during testing and are documented separately so anyone repeating the migration knows to expect them:

1. **Mouse event coordinates are no longer in logical render space.** SDL2's `SDL_RenderSetLogicalSize` automatically remapped `event.motion.x/y`, `event.button.x/y`, `event.wheel.x/y` into logical coords. SDL3's `SDL_SetRenderLogicalPresentation` does **not**. Mouse events arrive in window pixel coordinates. Fix: added virtual `BaseRenderEngine::convertWindowToRenderCoordinates(float &x, float &y)` (default identity), overridden in `RenderEngine` to call `SDL_RenderCoordinatesFromWindow(_renderer, x, y, ...)`. `LocalEvent::handleEvents` invokes it on each `SDL_EVENT_MOUSE_*` before dispatch. Symptom before fix: cursor appears far off-screen, click positions misaligned with on-screen widgets.
2. **`SDL_LOGICAL_PRESENTATION_INTEGER_SCALE` adds an extra downsample.** With `screen scaling type = nearest` the natural temptation is to map to `INTEGER_SCALE` mode, but that mode constrains the on-screen render to the largest integer multiple of the logical size — e.g., 2× (1280×960) on a 1920×1080 monitor. Combined with the physical-resolution Display buffer at 2.25× (1440×1080), the GPU does a redundant 1440→1280 downsample every frame. Use `SDL_LOGICAL_PRESENTATION_LETTERBOX` always, and let the texture's scale mode (`SDL_SetTextureScaleMode(_screenTexture, isNearestScaling() ? SDL_SCALEMODE_NEAREST : SDL_SCALEMODE_LINEAR)`) honour the user's preference. Symptom before fix: small details (small monsters in dialogs, fine UI) look blurry only on configurations where the integer-scale ratio differs from the physical-buffer ratio.
3. **`SDL_BITSPERPIXEL(SDL_PIXELFORMAT_XRGB8888)` returns 24, not 32.** SDL3's macro reports only colour bits; the storage is still 4 bytes/pixel. Existing code that switched on `surface->format->BitsPerPixel == 32` falls through to the `assert(0)` "unsupported format" branch. Fix: switch all such dispatch to `SDL_BYTESPERPIXEL` (returns 4 vs 1).
4. **Software cursor accumulates pixels in the framebuffer.** The pure-RGBA Display blits the cursor sprite directly into `_data` each frame; without a save/restore (which the indexed-buffer mirror used to provide implicitly), every frame stamps a new cursor on top of the previous one. Fix: do **not** blit the cursor into Display at all. Render the cursor as a **separate composite layer** at present time — `RenderEngine` keeps a small `_cursorTexture` (re-created when the sprite size changes), uploads the indexed→RGBA cursor pixels to it each frame, and renders it via `SDL_RenderTexture` with `SDL_BLENDMODE_BLEND` after the main framebuffer texture. The framebuffer stays clean, no save/restore needed.
5. **`SDL_CreateColorCursor` rejects negative hot spots in SDL3.** SDL2 silently accepted out-of-bounds hot spots. SDL3 returns NULL with `SDL_SetError("Cursor hot spot doesn't lie within cursor")`. Not actually hit by fheroes2 since `Cursor::SetOffset` already negates negative offsets back into [0, w/h) range, but worth knowing.
6. **`HOME` env var on Windows changes config dir.** When the user runs from git-bash, `HOME=C:\Users\<user>` is set, so `GetHomeDirectory` returns `~/.fheroes2` and writes log/cfg there. When run from PowerShell or VS Code's debugger, `HOME` is unset and `APPDATA` path is used (`~/AppData/Roaming/fheroes2`). Two parallel state directories. Pre-existing fheroes2 behavior, but a frequent debugging trap.
7. **`SDL_SetTextureScaleMode` doesn't survive `SDL_DestroyTexture` + `SDL_CreateTexture`.** When `_screenTexture` is reallocated lazily on the first frame after each resolution change, the freshly-created texture defaults to `SDL_SCALEMODE_LINEAR`. Combined with the `LOGICAL_PRESENTATION_LETTERBOX` from Surprise #2, the GPU bilinear-downsamples the physical-resolution texture into the logical 640×480 rect and back, smearing every game-pixel boundary — visible as rainbow noise on detail-heavy art (POL campaign-selection X_IVY background was the canary). Surprise #2 warned about choosing the wrong *presentation*; this one's about the *scale mode* regressing on every reallocation. Fix: re-call `SDL_SetTextureScaleMode(_screenTexture, isNearestScaling() ? SDL_SCALEMODE_NEAREST : SDL_SCALEMODE_LINEAR)` after every `SDL_CreateTexture`, not just the initial one. Landed in commit `aa5ab271e` along with several render-pipeline follow-ups: `paletteIdxToRGBA` now reads from a swappable 8-bit render palette so sprite blits track `Display::changePalette` again (relevant to Phase 5), `BlitRGBAScaled` / `BlitRGBAScaledAlpha` use alpha-weighted box-filter averaging on downscale (replaces nearest-neighbour), and two `*ToIndexed` callsites that silently OOB-read `GetPALColorId`'s 6-bit table got their `>> 2` input scaling.

#### Phase 1B — Surprise #8: SDL3_mixer 3.2.0 is a redesign, not a rename

The original Phase 1B sketch ("rename `Mix_OpenAudio` to take `SDL_AudioDeviceID` + `SDL_AudioSpec *`, swap `_RW` for `_IO`, done") is wrong. SDL3_mixer 3.2.0 (the version vcpkg ships) is a full rewrite with a new abstraction. All public symbols are now `MIX_*` (uppercase, no Mix_*-named compat layer). What's actually involved:

- **No `MIX_INIT_*` flags.** `MIX_Init()` takes no arguments and returns `bool`. Decoders are auto-registered. `MIX_GetNumAudioDecoders()` / `MIX_GetAudioDecoder(int)` enumerate what's actually available at runtime (FLAC, MP3, OGG, MIDI, MOD, WAV, AIFF, …).
- **No `Mix_OpenAudio` / `Mix_CloseAudio`.** Replaced by `MIX_CreateMixerDevice(SDL_AudioDeviceID, SDL_AudioSpec *)` returning a `MIX_Mixer *` opaque handle, paired with `MIX_DestroyMixer`. You can have multiple mixers; `nullptr`/`SDL_AUDIO_DEVICE_DEFAULT_PLAYBACK` for the default. Frequency/format/channels/chunksize are all `SDL_AudioSpec` fields; SDL3 negotiates with the device and auto-resamples whatever the app produces.
- **Channels → Tracks (paradigm shift).** Old: numbered "channels" (slots) you `Mix_PlayChannel` chunks on; queues live with the channel. New: a `MIX_Track *` is a handle you create explicitly with `MIX_CreateTrack(mixer)`, assign audio to with `MIX_SetTrackAudio(track, audio)`, then start with `MIX_PlayTrack(track, props_id)`. Tracks can be tagged for batch operations (`MIX_StopTag(mixer, "ui", 0)` halts every track tagged "ui"). The fheroes2 abstraction exposes channel IDs to callers (`Mixer::Play` returns a channel ID, `Mixer::Stop(id)`/`isPlaying(id)` use it) — implementation has to wrap an `int → MIX_Track*` table behind the existing API.
- **`Mix_Chunk` and `Mix_Music` unified into `MIX_Audio`.** `MIX_LoadAudio_IO(mixer, SDL_IOStream*, predecode, closeio)` for in-memory; `MIX_LoadAudio(mixer, path, predecode)` for files. The `predecode` flag picks chunk-style vs streaming behaviour. `MIX_DestroyAudio` for cleanup. So the existing `MusicInfo` class that lazily creates `Mix_Music` from a `std::variant<vector, string>` collapses to a `MIX_Audio *` cache keyed by music UID, owned by the music DB; only one needed per source.
- **Volume → gain (float, not int).** `Mix_Volume(channel, 0..128)` → `MIX_SetTrackGain(track, float)` and `MIX_SetMixerGain(mixer, float)` (master). 1.0 = unity, >1.0 = boost (with clipping risk), 0.0 = silent. The existing `normalizeToSDLVolume(int percentage)` exponential curve has to map to floats now: `MIX_MAX_VOLUME` is gone. Suggested: `gain = (exp(log(11) * pct/100) - 1) / 10.6`, no rescale to 128 needed.
- **Music finished hook → per-track stopped callback.** `Mix_HookMusicFinished` → `MIX_SetTrackStoppedCallback(musicTrack, cb, userdata)`. Same restart-on-finish logic, but registered against the dedicated music track instead of globally. Channel-finished bookkeeping (`Mix_ChannelFinished` → cleanup `Mix_Chunk`s) maps to per-track stopped callbacks too, but with the new `MIX_Audio` lifetime owned by the DB it's simpler — the audio is shared, not freed when the track stops. The dual-`Mix_Chunk` queue in `SoundSampleManager` collapses to just "destroy the track when it stops".
- **Music position resume.** `Mix_FadeInMusicPos(mus, 0, fadeMs, posSeconds)` → set `MIX_PROP_PLAY_START_MILLISECOND_NUMBER` + `MIX_PROP_PLAY_FADE_IN_MILLISECONDS_NUMBER` properties on the play options before calling `MIX_PlayTrack`. Or use `MIX_SetTrackPlaybackPosition(track, frames)` first. Note the property is in *milliseconds* (or sample frames, with `*_FRAMES_NUMBER`); the existing code stores position in seconds — convert at the call site.
- **3D positioning.** `Mix_SetPosition(channel, angle, distance)` → `MIX_SetTrack3DPosition(track, &MIX_Point3D)` with a 3-component float vector. The existing API takes `(angle_deg, distance_0_255)` — convert: `x = sin(angle_rad) * distance_norm`, `y = 0`, `z = -cos(angle_rad) * distance_norm`. 0 distance = at-listener; SDL3 attenuates with distance.
- **`Mix_AllocateChannels` is gone.** No fixed channel pool; tracks are created on demand. The existing `Mixer::SetChannels(num)` and `getChannelCount` map to "size of the int → MIX_Track* slot table". Or: keep no fixed table, return a generation-counter-style ID, look up via `MIX_GetTaggedTracks(mixer, "sfx", &count)` if needed.
- **MIDI config (timidity / SoundFonts) — confirmed absent from vcpkg's default install.** `Mix_SetSoundFonts` / `Mix_SetTimidityCfg` are gone from SDL3_mixer 3.2.0. Worse: vcpkg's `sdl3-mixer:x64-windows` defaults to `features core` only — **no MIDI / OGG / MP3 / FLAC decoder is built in at all**, only the bundled WAV reader. This was the root cause of the "all music is silent" Phase 1B bug discovered when first running the rewritten audio path: the in-memory MIDI bytes (XMI converted by `audio_xmi2mid.cpp`) failed to load with "Audio data is in unknown/unsupported/corrupt format" because no MIDI decoder was registered. Fix: install `sdl3-mixer[libvorbis,mpg123,libflac]:x64-windows --recurse` to add OGG/MP3/FLAC; add `[fluidsynth]` if MIDI fallback is desired (FluidSynth needs an SF2 SoundFont, wired through mixer properties — not yet implemented). For the Galaxy / GoG release the OGG path is preferred — the user's original CD-rip `Track02.ogg`..`Track42.ogg` files at `<HoMM2 install>/MUSIC/` match the `WIN_VERSION` naming scheme that `MUS::getFileName` searches for. **Action item also captured:** the build/{Debug,Release} dirs need a `music` junction next to `data` and `files`, pointing at the user's MUSIC/ folder. The existing `Music::setMidiSoundFonts` / `setMidiTimidityCfg` namespace stubs stay as no-ops until/unless MIDI fallback gets wired.
- **`SDL_RWops` → `SDL_IOStream`.** `SDL_RWFromConstMem` → `SDL_IOFromConstMem`, `SDL_FreeRW` → `SDL_CloseIO`. Same I/O abstraction, different name. Used for the in-memory music-from-`vector<uint8_t>` path.
- **`SDL_MIXER_VERSION_ATLEAST` is gone.** No conditional compilation against older mixer versions; we're 3.2.0+ unconditionally. Drop the `#if SDL_MIXER_VERSION_ATLEAST(2, 6, 0)` guard around `Mix_SetTimidityCfg`.

Reshape, not port. The 1126-line `audio.cpp` from commit `25d92f005` doesn't translate function-by-function; it needs the same public surface (`Audio::` / `Mixer::` / `Music::` namespaces unchanged so callers don't move) sitting on top of: a `MIX_Mixer*` singleton, a `std::map<int, MIX_Track*>` channel→track table for `Mixer::`, a dedicated music `MIX_Track*` for `Music::`, and a `std::map<uint64_t, MIX_Audio*>` cache for the music DB. The existing thread / mutex / `MusicRestartManager` worker stays valid — only the SDL_mixer call sites flip.

Reference: upstream SDL3 migration guide at https://wiki.libsdl.org/SDL3/README/migration ; SDL3_mixer header at `vcpkg/installed/x64-windows/include/SDL3_mixer/SDL_mixer.h`.

### Phase 2 — SDL_GPU pipeline alongside SDL_Renderer

Goal: build a parallel SDL_GPU rendering path that produces identical output to today, but using the GPU API. Keep `SDL_Renderer` doing real work; the GPU path is opt-in via a flag.

Add to `engine/screen.cpp`:
- `SDL_GPUDevice * _gpuDevice`
- `SDL_GPUSwapchain` setup on the existing window
- Compile + load composite shader (SPIR-V blob compiled at build time, loaded as a resource)
- `SDL_GPUGraphicsPipeline _compositePipeline` (one-time setup)
- `SDL_GPUSampler _nearestSampler`
- `SDL_GPUTexture _rgbaTex` at physical res (matches `display.bufferStride()/bufferHeight()`)

Initial composite pass (still no indexed channel — just verifying the GPU pipeline works):

```cpp
// Per frame in renderScreenRGBA:
SDL_GPUCommandBuffer * cmd = SDL_AcquireGPUCommandBuffer(_gpuDevice);
SDL_GPUTexture * swapchain = SDL_AcquireGPUSwapchainTexture(cmd, _window);

// Upload (dirty rect from display._prevRoi)
SDL_GPUTransferBuffer * upload = ...;
SDL_UploadToGPUTexture(cmd, _rgbaTex, display.image(), ...);

// Render pass
SDL_GPURenderPass * pass = SDL_BeginGPURenderPass(cmd, swapchain, ...);
SDL_BindGPUGraphicsPipeline(pass, _compositePipeline);
SDL_BindGPUFragmentSamplers(pass, 0, &(SDL_GPUTextureSamplerBinding){.texture = _rgbaTex, .sampler = _nearestSampler}, 1);
SDL_DrawGPUPrimitives(pass, 3, 1, 0, 0);  // fullscreen triangle
SDL_EndGPURenderPass(pass);

SDL_SubmitGPUCommandBuffer(cmd);
```

Switch over once visually identical. Decommission `SDL_Texture _screenTexture` and the `SDL_Renderer` from the framebuffer upload path. Keep `SDL_Renderer` only for any other 2D ops we still rely on (cursor compositing if not migrated, etc.).

Estimated: 1 week.

### Phase 3 — Add indexed channel + palette LUT

Wire up the second + third textures and switch the shader to the dual-channel composite.

Display-side additions:
```cpp
class Display final : public Image {
    // ... existing ...
    std::unique_ptr<uint8_t[]> _indexedBuffer;  // physW * physH bytes
    bool _indexedDirty{ true };
    Rect _indexedDirtyRoi;

public:
    const uint8_t * indexedBuffer() const { return _indexedBuffer.get(); }
    void markIndexedDirty( const Rect & roi );
};
```

`setResolution` allocates `_indexedBuffer` at physical dims alongside the existing RGBA buffer. `reset()` zeros both.

Engine-side additions:
- `SDL_GPUTexture _indexedTex` (R8 at physical res)
- `SDL_GPUTexture _paletteTex` (RGBA8 256x1)
- Per-frame upload of `_indexedTex` from `display.indexedBuffer()` (dirty-rect)
- Palette upload triggered by `Display::changePalette` (1KB blob)
- Update shader to the full composite (indexed + rgba + palette)

At this point cycling will work for any pixel whose indexed value is non-zero — even though no primitive is writing the indexed channel yet, so all pixels still resolve as RGBA. Visual identical to phase 2.

Estimated: 3-4 days.

### Phase 4 — Per-primitive dual-write

Mirror the per-primitive surgery from `PHYSICAL_RES_DISPLAY_PLAN.md` step 4, but adding the indexed write alongside the RGBA write. Use the same `PhysicalBlock` helper:

For indexed-source primitives (most of `image.cpp`):
- `BlitIndexedToRGBAOutput`, `AlphaBlitIndexedToRGBAOutput`, `CopyIndexedToRGBAOutput`
- `Fill`, `DrawBorder`, `DrawLine`, `SetPixel`, `ReplaceColorId` (RGBA branches)
- `ApplyRawPalette` (RGBA-out-from-indexed branch)

→ Write the **palette index** to the indexed buffer block. Skip the RGBA write entirely (shader picks indexed because idx > 0.5).

Exception: shadows. The transform values 2-5 darken the destination's existing RGB. With dual-channel, "darken the existing pixel" is ambiguous — the visible pixel might be coming from either channel. Simplest answer: shadow ops *materialize* the indexed pixel as RGBA (palette lookup → write RGBA, write 0 to indexed), then darken the RGBA. Cycling no longer applies to shadowed pixels. Acceptable; shadows are rare overlays.

For RGBA-source primitives:
- `BlitRGBAScaled`, `BlitRGBAScaledAlpha`, `BlitRGBAAlpha`
- `BlitRGBAToRGBAOutput`, `AlphaBlitRGBAToRGBAOutput`, `CopyRGBAToRGBAOutput`
- `DrawLineRGBA`, `CopyRGBA`, `DimRGBA`
- Smacker video frames (`smk_decoder.cpp`)
- Battle spell-effect scratch copies

→ Write **RGBA** as today. Write **0** to the indexed buffer block (= "I'm RGBA now, ignore any old palette index here").

Mixed primitives (`AlphaBlitIndexedToRGBAOutput` with alpha < 255): the result is a blended RGB that doesn't correspond to a single palette index. Treat as RGBA: materialize the source palette index, blend, write to RGBA, clear indexed. Cycling doesn't apply to alpha-blended sprites (which is the current behaviour anyway).

**Defensive: harden `GetPALColorId` first.** The 6-bit RGB lookup table (`rgbToId[64*64*64]`) has no bounds check, and any caller that accidentally passes 8-bit values silently OOB-reads up to 1 MB past the table — commit `aa5ab271e` fixed two such cases (`BlitRGBAToIndexed`, `AlphaBlitRGBAToIndexed`) but Phase 4 introduces *more* `*ToIndexed` write sites. Either shift/mask the input internally (and remove the existing explicit `>> 2` from each caller) or add `assert((red | green | blue) < 64)` in debug builds. The latter is one line and catches new offenders during phase-4 visual checks instead of producing weird garbled palette indices on screen.

This is the bulk of the work — same scope as the physical-res refactor's step 4 (~80% in `image.cpp`). Land one primitive at a time with a visual check after each.

Estimated: 1 week.

### Phase 5 — Palette upload hook + cycling animation tick

`Display::changePalette` triggers a re-upload of the palette texture. With the GPU shader, that's all that's needed — every pixel that has a non-zero indexed value resamples through the new palette next frame.

The hook exists already: `Display::changePalette(p)` calls `fheroes2::setRenderPalette8Bit(p)` (in `image_palette.{h,cpp}`, introduced in commit `aa5ab271e`) so CPU-side `paletteIdxToRGBA` already tracks palette changes. Add the GPU upload right next to the `setRenderPalette8Bit` call — same lifetime, same trigger, no new injection point needed.

**Caveat**: `ui_tool.cpp::colorFade` (line 489) passes a raw 6-bit `getGamePalette()` pointer to `screenRestorer.changePalette` — interpreting 6-bit values as 8-bit produces one too-dark fade frame at end of video. Harmless today (the screenRestorer dtor restores defaults a frame later), but once cycling reactivates and the GPU palette texture reads from the same source path, the misinterpretation can become a longer-lived glitch. Fix while you're here: pass `nullptr` (lets the default kick in) or `PALPalette()` (the 8-bit shifted copy already maintained for this purpose).

Re-enable color cycling animations (gold/water/lava). Find where the cycling tick was disabled or no-op'd (`agg_image.cpp` cycling preprocessing) and reactivate.

Estimated: 1-2 days.

### Phase 7 (optional follow-ups, future sessions)

Once the GPU pipeline is in place, the door is open for:
- **Custom monster shaders**: per-monster fragment shaders that do channel-wise transforms on the base sprite. Replaces palette-table generation in `pal.cpp` for custom monsters with shader uniforms (tint color, gradient stops, etc.). Drops shipping hi-res PNGs for monsters that just need a recolor.
- **GPU effects**: bloom (`agg_image.cpp::CreateHolyShoutEffectRGBA` could become a shader pass), CRT/scanline filter as a post-process, smooth screen fades.
- **Higher-bit palette**: the current 6-bit-per-channel palette could become 8-bit on GPU side. Requires extending `paletteIdxToRGBA` upstream, or doing the bit-shift in the shader.
- **Cycling timing on GPU clock**: cycling tick driven by uniform `time` instead of CPU-side palette table updates. Reduces the per-frame palette upload to never (palette is constant; only the cycling phase changes).

## Risks and gotchas

- **Shader compilation toolchain**: SDL_shadercross translates SPIR-V to MSL/HLSL/DXIL. We can either:
  - Pre-compile shaders at build time and ship per-platform blobs (simpler distribution, requires shadercross + glslang in the build pipeline)
  - Compile at runtime via SDL_shadercross (heavier startup, simpler build)
  - Recommended: pre-compile, ship blobs in `files/data/shaders/`
- **Android backend**: SDL_GPU on Android uses Vulkan. Target device — Samsung Galaxy A56 — has the Xclipse 540 GPU (AMD RDNA3-based, in the Exynos 1580 SoC) with Vulkan 1.3 support, so SDL_GPU runs natively without any fallback path. Lower-end Android devices without Vulkan 1.0+ would need SDL_Renderer fallback, but that's not a constraint for this project.
- **PSV port**: dropped from scope. `engine/screen.cpp`'s `#if defined(TARGET_PS_VITA)` blocks (vita2d-based) can be deleted along with the SDL2 migration; we're not maintaining PSV.
- **Mixer migration risk**: SDL3_mixer is younger than SDL2_mixer; some features may behave differently. The MIDI path in particular is finicky. Test on Windows Media Foundation, Linux fluidsynth, macOS AU.
- **Existing `SDL_Surface`-based code**: the legacy palette setup (`copyImageToSurface`, `_palette8Bit`) is dead in the pure-RGBA world but the source still has the helpers. Phase 1 should delete or stub them; they don't translate to GPU anyway.
- **Memory cost**: an R8 indexed buffer at 1920x1440 is ~2.7 MB CPU-side. RGBA at the same res is ~11 MB. Total ~14 MB CPU framebuffer + same on GPU. Fine for desktop; tight on memory-constrained mobile.
- **Per-frame upload cost**: 14 MB upload at 60 FPS = 840 MB/s. Modern PCIe handles this trivially; mobile/integrated GPUs less so. Use dirty-rect uploads (the `_prevRoi` mechanism in `Display::render` already tracks the dirty area — extend that to drive the GPU upload extents).
- **Shadow ambiguity**: the "shadows materialise indexed → RGBA" rule means cycling stops at shadowed pixels. Verify visually; if it bothers, alternative is a third channel that records "shadow mask" and the shader applies it to the resolved color. Adds an R8 channel; probably overkill.
- **Synchronisation between palette upload and frame composite**: must upload the palette texture before the render pass that uses it, in the same command buffer. Standard SDL_GPU usage; just don't forget the resource barrier.

## What does NOT need to change

The physical-resolution Display refactor stays as-is. `bufferStride()`, `bufferHeight()`, `physicalScale()` still drive primitive block expansion — they just write to two channels instead of one.

`Image`, `Sprite`, `ImageRestorer`, the palette tables in `pal.cpp`, the ICN sprite cache, the AGG asset loader — all unchanged. The custom-monster generation pipeline in `agg_image.cpp` could later move to shader-based transforms (phase 7), but doesn't have to.

Game logic, AI, network, save/load, audio, input — entirely orthogonal to this refactor.

The hi-res monster pipeline (Thor / Succubus / Azure Dragon / Blood Dragon / Avenger PNGs) keeps working unchanged — they take the RGBA-source dual-write path that's already there.
